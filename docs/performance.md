# Общая выдача вместо работы на каждого зрителя

Сервер получает вложения всех постов один раз в общий индекс. Основные изменения публичного режима:

- Вместо персонального POST каждые 10 секунд — общие GET-порции: канал, одна из восьми корзин, длительность, переключатель 18+. Идентификатора пользователя и списка просмотренного в URL нет.
- Один и тот же готовый JSON обслуживает многих зрителей. Повторяются ни выборка, ни сериализация. nginx отдаёт кеш; ETag позволяет ответить 304 без тела, если данные не изменились.
- Коллекция собирается в браузере из общих порций её каналов. Каждая комбинация источников не создаёт отдельную серверную выборку. Очередь оставляет место для каждой выбранной ветки.
- Браузер перемешивает кандидатов, применяет интересы, скрытые и просмотренные ролики. За следующей порцией идёт при остатке меньше 24 кандидатов, а не по таймеру каждые 10 секунд. Пауза на длинном ролике не вызывает постоянной загрузки новых порций.
- Дерево и раскрытые доски обновляются примерно раз в минуту вместо 5 и 4 секунд. Скрытая вкладка прекращает запросы метаданных. Пустые порции имеют короткий кеш, чтобы не затягивать первый запуск.
- В ответе дерева — два примера на доску вместо двенадцати. Счётчики по всем вложениям и фильтрам сохраняются. При выборе треда его ролики загружаются отдельной общей порцией.
- Реестр досок хранится в памяти и обновляется одним общим запросом, а не читается и разбирается с диска для каждого посетителя.

Видео по-прежнему идут непосредственно с Двача в браузер. На VPS нет проксирования или перекодирования медиапотока; буферы соседних роликов остаются в браузере.

## Замер на том же VPS, 13 сентября 2026

Зафиксирован снимок индекса из **32 046 роликов**. Скрипт `scripts/benchmark-radio.mjs` сравнивает 1 000 подготовок порции общего эфира на одинаковом снимке. Старый путь выбирает и сериализует каждый ответ; новый строит восемь порций и переиспользует их.

| Подготовка 1 000 ответов | Раньше | Общие порции |
|---|---:|---:|
| CPU | 9 575 мс | 102 мс |
| Время выполнения | 11 320 мс | 161 мс |
| Построено порций | 1 000 | 8 |
| Взято готовых порций | 0 | 992 |

На одном и том же ответе дерева сокращение примеров уменьшило JSON с 418 622 до 100 235 байт; gzip уровня 1 — со 121 958 до 28 265 байт. Это примерно в 4,3 раза меньше передаваемых данных дерева, без изменения счётчиков.

Кеш этих восьми ответов занял около 204 КБ JSON. Экономия CPU на **этом участке** — примерно 94 раза. Это не означает, что весь сайт стал быстрее в 94 раза, и не является доказательством поддержки конкретного числа одновременных зрителей.

Живой HTTP-замер на том же VPS: по 120 запросов к Node.js, четыре параллельных соединения. После изменений GET-порция была предварительно прогрета; все ответы имели один ETag.

| HTTP-путь | Суммарное время | p50 | p95 | Тело ответов суммарно |
|---|---:|---:|---:|---:|
| Прежний POST | 2 706 мс | 79,5 мс | 191,7 мс | 3,10 МБ |
| Общий GET | 593 мс | 17,4 мс | 52,3 мс | 3,08 МБ |
| GET с If-None-Match | 259 мс | 6,7 мс | 15,7 мс | 0 байт |

Все запросы завершились ожидаемыми 200 или 304. Это отдельные измерения живого сервера с работающим индексатором и меняющимся индексом, а не контролируемое сравнение CPU выше. Генератор запросов также работал на VPS. На публичном HTTPS отдельно проверен переход `X-WebMTV-Cache: MISS → HIT` с неизменным ETag: nginx действительно отдаёт готовую порцию без Node.js.

Повторить CPU-замер из папки приложения на сервере:

```sh
/opt/webmtv-node/bin/node --import tsx scripts/benchmark-radio.mjs /path/to/frozen-library.json 1000
```

Скрипт читает снимок и реестр, не изменяет рабочий индекс. Для сравнения нужен один и тот же снимок и одинаковое окружение.

## Что ограничивает результат

Кеш JSON ограничен 128 записями и 8 МиБ сериализованных данных; соответствующие объекты занимают дополнительную память. Это не бесконечное хранение всех каналов. Редкие запросы и вытесненные порции потребуют нового построения. Обновления могут появляться с задержкой около минуты; во время восстановления сервера nginx может временно отдавать старый кеш.

Восемь корзин дают разнообразие кандидатов, но не являются полным каталогом: возможны повторы между корзинами. Просмотренное фильтруется локально; после исчерпания доступного материала допустим повторный проход. Маленький тред не превращается в бесконечный поток новых роликов.

Для примера, 96 свежих кандидатов при просмотре одного ролика каждые 20 секунд дают около 24 минут до порога пополнения. Это расчёт для такого поведения, а не измеренное среднее. Быстрые свайпы, скрытые ролики и уже просмотренные кандидаты увеличивают число запросов.

Остаются сетевой трафик метаданных, TLS, периодический общий обход источника и запись индекса. Ограничения nginx и ресурсов процесса сохранены. От объёмной атаки на канал VPS эта оптимизация не защищает. Новые серверы, платные сервисы и внешний CDN не добавлены.

## Старт и переключение видео, 13 сентября 2026

После жалобы на медленный просмотр отдельно проверен медиапуть. Приложение передаёт URL в HTML video, не скачивает файл в blob и не ждёт его целиком. В браузере WebM длительностью 78 секунд уже воспроизводился на отметке 9,4 секунды при буфере только до 55 секунд.

Что исправлено в плеере:

- Следующий файл получает `src` только после начала воспроизведения текущего и появления четырёх секунд запаса либо полной загрузки короткого ролика. До первого кадра соседний файл не конкурирует за соединение.
- Предыдущий ролик сохраняет свой слот и буфер; отсутствующий предыдущий файл не скачивается на всякий случай. Переход на ещё не подготовленный ролик тоже сохраняет текущий слот для возврата.
- При ожидании данных отменяется незавершённая подготовка соседа. Неактивным слотам разрешена только загрузка метаданных, кроме следующего при достаточном буфере. `preload` — подсказка браузеру, а не жёсткий лимит байтов: [MDN](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/preload).
- Ошибка фоновой загрузки заменяет подготовленного кандидата, не дожидаясь перехода на битое видео. Повторный выбор ошибочного слота из истории перезапускает загрузку, чтобы ошибка не оставалась без события.
- Соединение с основным медиадоменом прогревается через `preconnect` при открытии страницы.

На сети разработчика восемь ограниченных запросов первых 64 КиБ получили HTTP 206 за 0,63–3,00 секунды, первый байт — за 0,49–2,80 секунды. Это время ответа Двача, а не нашего API. У двух из шести проверенных MP4 блок `moov` отсутствовал в первых 64 КиБ: контейнер может требовать дополнительных чтений перед стартом. Это не доказательство скачивания целого файла.

В браузерной проверке обновлённого плеера в момент старта URL был только у активного слота; затем появился подготовленный сосед. После нажатия «Дальше» проверка через 299 мс застала воспроизведение на 0,176 секунды, после «Назад» через 346 мс — на 0,209 секунды, с сохранёнными буферами. Время включает автоматизацию; это два наблюдения, не распределение задержек и не сравнение одинаковых файлов до/после. Сеть друга и реальный iPhone в этом замере не проверены.

Проксирование всех видео и перекодирование на однопроцессорном VPS не включены: они перенесли бы весь медиатрафик зрителей на наш канал. Скорость исходного медиасервера и маршрута зрителя по-прежнему ограничивает холодный старт.
